# 主要処理の性能計測・改善（2026-10-02）

## 範囲と条件

主要ユーザー操作15種類を、敵10/100/250体の固定fixtureで計測した。各サイズ3回warmup後12反復、中央値と観測p95（nearest-rank）を使用。ネイティブChromium 154.0.8037.57、クラウドLinux、1440×900、ANGLE Vulkan SwiftShader。ユーザーPC／実GPUの保証ではない。Before/Afterで同じfixture・操作順・反復数を使用した。

独立したCore計測は78ケース。V1/V2/V3と全Algorithm Lab、検証、編集、Play、JSON、1/10階、シミュレーションを5回warmup後30または100反復で計測した。

AI待ち時間はローカルstubに置き換えたため、ライブOpenAIの遅延・料金・レート制限時の実時間は未測定。ユーザーの確認待ち、OSの保存先選択／実ディスク書込、公開CDNからの初回読込、全ブラウザ／全ハードウェアも対象外。『全関数・全経路を測った』という主張ではない。JSON出力の測定はデータ構築と文字列化まで。

## 確認されたボトルネック

1. Playの状態だけが変わっても、同一DungeonSpecから通路経路とシーン計画を毎回再計算していた。Beforeの戦闘操作では、この段階だけで約468〜505ms、戦闘Core自体は約0.3〜2msだった
2. 通路経路は各ドア方向・オフセット候補を探索していた。既存の最良スコアを数学的に改善できない候補も探索していた
3. 大きな敵グループの入室起動は敵ごとにゲーム状態を複製しており、二次的なコストが発生していた

## 実施した改善

- renderer非依存のシーン計画を入力内容と描画styleに基づく16件LRUで再利用。各呼び出しでSpec検証し、返却値を複製してキャッシュ汚染を防ぐ。配置・Entity・style変更時には別キーになる
- 経路長のManhattan下界と既知のペナルティで、現在の最良経路を改善できない候補だけを除外。負のbendPenaltyには適用しない。旧実装との48ケース比較で成功34ケースと失敗14ケースが一致した
- 既に複製済みのイベント候補に敵起動状態を一括適用。状態・イベント順序・one-shot・失敗時ロールバックを維持。125体は中央値5.17→0.295ms、250体22.98→0.614ms
- 1回の同期UI更新中の途中描画をまとめ、最終状態を1回描画する。測定した戦闘操作は6 draw→1 draw。例外時・入れ子・戻り値を単体テストし、最終表示はnative smokeで検証
- 計測probeは明示的なローカル計測時のみ有効。無効時は処理をそのまま実行し、永続化・外部送信・プロンプト記録を行わない

## 再現と残る負荷

- UI: PROFILE_PHASE=before / after として scripts/profile-user-flows.mjs を実行。保存済みBeforeが最適化前の基準値であり、現在コードでbeforeラベルを使っても旧コードを復元するわけではない
- Core: scripts/profile-special-room-core.mjs
- JSON evidence: artifacts/performance/ui-before.json、ui-after.json、router-equivalence.json
- Core evidence: artifacts/special-rooms/core-profile-before.json、spawn-batch-profile.json

250体の操作ではシーンオブジェクト再構築・描画コストが残る。通常100／高度設定250の上限は維持する。大きなシミュレーションも250体全処理で中央値約526msあり、繰り返しのsession/trace複製が主な残存コスト。今回は広範な可変状態化や戦闘仕様変更を避けた。1ms未満の検証・JSON処理は環境ノイズが目立ち、一部の微小な増減を改善／劣化と断定しない。

## 攻略経路検証を含む最終生成コスト

新しい有限の攻略例検証を含め、5warmup・30反復・2Seed×3難易度で測定。1階は中央値5.7〜15.1ms／p95 6.7〜20.2ms、3階14.7〜18.9／15.5〜28.4ms、10階37.9〜46.4／44.7〜66.2ms。以前のsub-ms生成Core値はこの実Play検証追加前であり、最終V3全体の値と混同しない。
